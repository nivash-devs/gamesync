GameSync data flow

How edits move between the relay server and each person's Godot project.

Scenes Files Live scripts Presence and cursors

Computers never talk to each other directly. Every change goes up to the server, which updates the room's copy and forwards it to everyone else in the room. The sender never gets its own change back.

The four channels

Scenes

The open scene is snapshotted, and only the properties that changed are sent, up to 20 times a second.

set add remove

Files

The project is scanned once a second and files are compared by MD5. Changed files are sent whole, up to 8 MB. Scripts, scenes and other text are gzipped first, usually to a quarter of the size or less.

fput fdel file

Live scripts

Typing turns into small insert and delete ops. The server orders them, and each client transforms them (OT).

dop dack dstate

Presence

Who is in the room, their color, what they have selected, and where their text cursor is.

presence select dcur

Joining a room

The room's files win. Before a local file is overwritten, it is copied to user://gamesync_backup. Files that only exist locally are uploaded. Nothing local is deleted on join.

One edit, end to end

Moving a node

  1. A drags Player. The 20 Hz snapshot sees that position changed.
  2. A sends set { scene, path: "Player", props: { position: ["v2", x, y] } }.
  3. The server stores it in the room's scene and forwards it to everyone who has that scene open.
  4. B decodes the tagged value into a Vector2 and sets it on the node. The scene is marked unsaved, at most every 0.5 s.

Typing in a script

  1. A types. About 30 times a second, a Myers diff turns the change into an op such as [12, "x"] (keep 12, insert "x").
  2. A sends dop { path, rev, op }. Further typing is held in a buffer until the server answers.
  3. The server transforms the op past any edits A hadn't seen yet, applies it, bumps rev, and replies dack to A and dop to the others.
  4. B transforms the incoming op past its own unsent typing and applies it line by line in the CodeEdit.

ot.js on the server and ot.gd in the plugin must behave identically. The test suite fuzzes 20,000 random edit pairs to check this.

Saving an image or sound

  1. The once-a-second scan sees a new MD5.
  2. A sends fput { path, md5, data }. Images and sounds go as they are; text files go gzipped with z: 1.
  3. The server stores it (up to 300 MB per room) and sends file to everyone else.
  4. B writes it into res:// and tells the editor to rescan.

When things go wrong

  • Server asleep: the free plan sleeps after 15 minutes idle. The plugin retries every 3 s for up to 100 s while it wakes up.
  • Connection lost: the plugin rejoins the same room code on its own and resends its scene and file list. A server restart (for example a redeploy) wipes all rooms, so the first person back seeds the room again.
  • Room empty: when the last person leaves, the room and everything in it is deleted from memory. Each person's project on disk is the lasting copy.
  • Bad edit: if an op doesn't fit, the server sends dstate with the full text and the client resets to it.
